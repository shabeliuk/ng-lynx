# 40 — The Lynx 4.2 upgrade

What moved, what changed in ng-lynx because of it, what engine 4.2
fixes, and what was measured on Explorer 4.1 and 4.2. Like
[39 — The Lynx 4.1 upgrade](39-lynx-4-1.md), everything here was checked
against the published packages or a build, or measured on a device.

## Two version axes, again

**Engine 4.2.0** (`lynx-family/lynx`, tag `4.2.0`, released 2026-10-27) is
what runs the bundle. Its GitHub release has no written notes, only the
artifacts, Explorer included. The **npm toolchain** has its own numbers:
`@lynx-js/rspeedy` 0.18.4 is the one that pairs with it. Bundles still declare
engine **3.2**, the template plugin's default, so the same bundle loads on 4.1
and 4.2. Measured on both below.

## What changed in ng-lynx

### The build engine and the template plugin

Since rspeedy 0.17 a **build engine** (`@lynx-js/rsbuild-plugin`, applied
automatically) owns the template plugin and exposes its class as
`Symbol.for('LynxTemplatePlugin')`. `pluginLynxConfig` taps the hooks of that
exposed class. `pluginAngularLynx` registers instances of its own import, so
the two only meet when the package manager installs **one copy** of
`@lynx-js/template-webpack-plugin`. With two, `pluginLynxConfig({
enableCSSRule: true })` would silently stop reaching our bundles, dropping
`@media` without an error. Today there's one copy (both ask for `^0.16.6`),
and a build-time probe confirmed the exposed class is ours. The plugin now
warns at build time if they ever diverge.

### `engineVersion`

ReactLynx renamed `targetSdkVersion` to `engineVersion`, and the docs use
the new name. `pluginAngularLynx` now takes `engineVersion` too, keeping
`targetSdkVersion` as an alias, and warns if both are set to different
values. The template plugin itself still takes `targetSdkVersion`; the plugin
maps one onto the other, as ReactLynx does.

### The encoder still stops at 3.9

`@lynx-js/tasm` 0.0.51 "update[s] supported lynx version to 4.2", but
`@lynx-js/template-webpack-plugin` 0.16.6 pins 0.0.49 exactly. Measured: a
build with `engineVersion: '4.0'` fails with `current compiler only support
lynx version [1.0, 3.9], but engine version is 4.0`. So
[13 — Styling](13-styling.md#media-queries)'s advice stands: `@media` apps
declare 3.9, and 4.0 waits for a template plugin release on tasm 0.0.51+. A
repo-level pnpm override would only change this repo's builds, not what
users of the package get, so there isn't one.

### ReactLynx's worklet runtime moved

> Since 1.0.0 ng-lynx has its own worklet runtime and no longer depends on
> `@lynx-js/react`: see [42 — The worklet runtime](42-worklet-runtime.md). This
> section is how the 4.2 upgrade went.

ng-lynx bundles `@lynx-js/react`'s main-thread worklet runtime for
`[lynxMainThread]`. ReactLynx 0.128 added `@lynx-js/react/worklet-runtime/init`,
and 0.129 removed the old `@lynx-js/react/worklet-runtime` export the plugin
resolved. Read from the published 0.129.1 source: `init` still installs the
same globals (`lynxWorkletImpl`, `registerWorkletInternal`) when evaluated, so
the plugin now resolves `init` first and falls back to the old entry.

GenUI 0.7's `@lynx-js/react-signals` 0.0.7 accepts ReactLynx up to 0.129, and
its `react-rsbuild-plugin` peers on `^0.128 || ^0.129`, so everything moved to
0.129.1 together (one copy). Measured on 4.2, iOS and Android: the `worklet`
example's dim, `runOnBackground` count, ref reset and `lynxAnimate` fade all
work through the `init` entry.

### Found on the way: production worklet builds didn't load

`examples/worklet`'s production build failed on Explorer 4.1 with "can't
derive a worklet id from an anonymous function". The build engine minifies
with `compress.inline: 2`, which folds the single-use
`function pressFadeMT(ctx) {…}` into `defineWorklet(function (e) {…})`, and
`defineWorklet` takes its id from `fn.name`. The minifier settings are the
same in build engine 0.1.2 and 0.1.7, so this wasn't caused by the upgrade.
Dev builds aren't minified, which is why earlier passes, all on dev servers,
never saw it. When `mainThreadModules` is set, `pluginAngularLynx` now adds
`keep_fnames: true` to `compress` and `mangle`. Measured afterwards on 4.1 and
4.2: tap to dim, the `runOnBackground` count, reset through a main-thread
ref, and the `lynxAnimate` fade all work. See
[11 — Worklets](11-worklets.md).

### Upstream noise

On Node 26 every rspeedy command prints `DEP0205: module.register() is
deprecated`. The trace points into rspeedy's config loader
(`@lynx-js/rspeedy/dist/register`), not into ng-lynx.

### Sparkling (the native iOS app in `examples/genui`)

No newer Sparkling exists: `2.1.0-rc.36` (2026-08-11) is the latest release
on npm and GitHub; the stable line is `2.0.1`. Sparkling's `main` has three
later commits (an Android container-restore fix, a playground fix, docs) but
no release, and it still depends on rspeedy `^0.13.3`, which is where the
Rsbuild 1.7.3 peer warning comes from. Separately, the app's `Podfile` pins
the engine itself (`pod 'Lynx', '3.9.0'`, with XElement 3.9.0 and PrimJS
3.8.0-alpha.6); Sparkling doesn't force that version. Moving the native app
to the 4.2 pods is a step of its own: `pod install`, then a check that
Sparkling rc.36 still builds against 4.2.

### GenUI 0.7

`@lynx-js/genui` 0.4.0 → 0.7.2 (and `@openuidev/lang-core` 0.2.18 → 0.3.2,
whose 0.3.0 only unified version numbers). Every import path we use still
exists. What changed for the Angular OpenUI port:

- **`@Append(array, item)`.** GenUI 0.7's system prompt teaches it, but GenUI
  registers it into lang-core only from its prompt library and its ReactLynx
  renderer, neither of which is in an Angular bundle. Measured: with
  lang-core alone the builtin is absent. `createOpenUiLibrary` and
  `OpenUiState` now register upstream's definition (`openui/builtins.ts`).
- **State-driven children didn't render.** `Stack(@Each($items, …))` arrives
  as an unevaluated expression, and the node directive passed `children`
  through unevaluated. Found by the new harness; older than 0.7, but
  `@Append` exists to grow such lists. Expression children are now evaluated.
- **Nodes update in place.** GenUI 0.7 keys React children by statement id,
  then `id`/`name`, then type and position, so components survive edits. The
  node directive now applies the same identity: a new node for the same
  element updates the component instead of rebuilding it (a negative control
  confirmed the harness catches a rebuild).
- **`Canvas`** joined the default catalog. Upstream draws only on Web, by
  `eval`-ing the model's code; on iOS/Android it shows "Canvas is not
  supported on this platform." The port renders that fallback everywhere.
  The planner's prompt adds a rule keeping the model off it.
- **Prompt drift beyond signatures.** Component order, groups and the `List`
  description had drifted unnoticed. `createOpenUiLibrary` now assembles the
  library like upstream (`componentNames`, `includeDefaultComponents`,
  `componentGroups`), and `verify:genui-openui-parity` compares the whole
  generated prompt.
- Action plans already read live state (upstream's 0.7.2 `actionContext`
  fix); `verify:genui-openui-append` pins it. `@lynx-js/lynx-ui` is an
  optional peer and none of our five GenUI entry points reaches it.
- The catalog extractor now sorts enum values; `verify:genui-tools` compares
  them as a set.

## What engine 4.2 brings

With no release notes, this comes from the typings (`@lynx-js/types`, whose
entries carry per-platform `@since` tags) and the 551 commits between the
`4.1.0` and `4.2.0` tags. None of the fixes below was reproduced on its own;
the measurements further down cover what this repo uses.

**New developer-facing surface** (now typed on the directives):

- `<scroll-view experimental-android-enable-new-overflow>`: Android 4.2, the
  new overflow clipping, on by default.
- `<scroll-coordinator android-adapt-to-empty-slot>`: Android, new in 4.2
  (absent from the 4.1.x source), off by default.
- `<overlay android-navigation-bar-style>`: Android 4.1, typed now as well.
- `<inline-image loop-count>` on Android (4.2).

**Fixes that touch features this repo uses:**

- `<list>`: native lists now use a "decoupled" implementation; plus nested
  scrolling in list containers (Android) and scroll offset in horizontal RTL.
- `<scroll-coordinator>` on Android: no more blank content, stable slot
  boundaries, and expansion after the app shrinks.
- Gestures: detector lifecycle across list-item reuse; iOS no longer cancels
  active gestures on a detector refresh; Android ancestor pan interception
  inside scroll containers.
- CSS: `@media` evaluates against the viewport in CSS logical pixels; cascade
  layers (`@layer`) are ordered; duplicated selectors keep their values in a
  class merge; CSS variables track transitive dependencies; computed lengths
  come back in CSS pixels (what `getComputedStyleProperty` returns).
- Events and input: iOS touch identifiers are stable; Android uses the
  platform touch slop as the long-press cancel threshold; iOS `<textarea>`
  refreshes text attributes and fixes an empty auto height.
- Runtime: fetch header names are case-insensitive; `Promise.allSettled` is
  supported (ng-lynx's polyfill stays for older engines); attribute
  updates override pending resets in the same flush.

**Unchanged:** Explorer 4.2.0 still doesn't report the system colour scheme
to `prefers-color-scheme`. Its `develop` branch does, so a later release
should. Measured: dark mode on 4.2 leaves the `light scheme` chip lit, and the
host-theme fallback in `examples/responsive` still turns the page dark.

## Not done

- **Canvas drawing** in the Angular port (deliberately not ported, see above).
- **Engine floor 4.0 for `@media` apps**, which waits for the template plugin
  to move to tasm 0.0.51+.
- **`prefers-color-scheme`**, which waits for an Explorer release that reports
  the scheme.
- **Not run on 4.2:** `router`, `media`, `threejs-*`, `i18n` and the rest, on
  either platform. See [41 — Device testing](41-device-testing.md).
