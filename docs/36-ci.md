# CI & publishing

Three GitHub Actions workflows, all under `.github/workflows/`.

## `DO_NOT_TRACK=1` — set at workflow level in both

Since `@lynx-js/genui` 0.4.0 widened its `@openuidev/lang-core` range to
`^0.2.11`, that package resolves to 0.2.18, which ships a `postinstall` that
reports pseudonymous install telemetry to PostHog — a salted project id,
OpenUI/Node/OS/package-manager metadata, and the IP PostHog observes. (0.2.9,
the version pinned before, has no `postinstall` at all.)

Both workflows therefore set `DO_NOT_TRACK: '1'` at the **workflow** level, so
every job's `pnpm install` inherits it. Verified rather than assumed: the
opt-out predicate in the shipped bundle is

```js
function isTruthyEnv(value) { return value === '1' || value?.toLowerCase() === 'true'; }
function isTelemetryDisabled(env) {
  return isTruthyEnv(env?.['OPENUI_TELEMETRY_DISABLED']) || isTruthyEnv(env?.['DO_NOT_TRACK']);
}
```

and running the postinstall with `DO_NOT_TRACK=1` while instrumenting
`http.request` / `https.request` / `fetch` produced **no outbound calls**.
`OPENUI_TELEMETRY_DISABLED=1` is the vendor-specific equivalent;
`DO_NOT_TRACK` is preferred because it is the cross-vendor convention.

Workflow-level `env` merges with (rather than replaces) the step-level `env`
blocks already in use, such as `NODE_AUTH_TOKEN` in `release.yml`.

> **Local installs are not covered.** This only sets the variable inside CI. A
> contributor running `pnpm install` on their own machine still triggers the
> postinstall unless they export `DO_NOT_TRACK=1` themselves.

## `ci.yml` — on every push to `main` and every PR

Four jobs:

### `verify` — build + typecheck + the full harness suite

**Node 22 only**, on the pinned Angular (21):

```
pnpm install --frozen-lockfile
pnpm --filter angular-lynx build       # tsc -b + ngc partial + schematics
pnpm --filter angular-lynx typecheck   # tsc -p tsconfig.json (whole program)
pnpm --filter angular-lynx verify:all  # every verify:* harness (see below)
```

`verify:all` (`packages/angular-lynx/verify/run-all.mjs`) runs every
`verify:*` script sequentially and fails on the first red one, printing that
harness's own assertion output. Env knobs: `VERIFY_ONLY=a,b`, `VERIFY_SKIP=a,b`,
`VERIFY_LIST=1`.

Because the harnesses compile components through Angular's **JIT** compiler in
Node, this job is the **JIT** half of the "AOT/JIT" matrix. The `examples` job
is the **AOT** half.

**Why not Node 20.** `verify:i18n`, `verify:lazy-chunks`, `verify:asset-url-build` and
`verify:schematics` each run a real `rspeedy build` for the `web` target, and on Node 20 that fails
with `WebAssembly.Module(): … Unknown heap type -14`: Rspack's toolchain needs
WasmGC, which Node 20's V8 doesn't have, on any patch and with any flag. So
`engines.node` is `>=22.12.0` everywhere, the floor rspeedy declares above 20.

### `examples` — real AOT builds (compile + package smoke test)

Builds a representative set of examples with `rspeedy` (AOT/ngtsc by default) —
`hello-world`, `ng-forms`, `worklet` and `product-detail` (main-thread modules),
`styling` (Sass), `tailwind`, `control-theme` (the themed control kit), `responsive`
(`@media`), and `genui` with its unit tests. This catches template/AOT/config regressions the mock
harnesses can't (a broken `@Component`, a bad `lynx.config.ts`, a missing typed
element). `router` / `i18n` / `lazy-chunks` aren't in this list because the
verify suite already builds them (the last two run real `rspeedy build`s inside
their harnesses).

**Where's the ES2019 parse gate?** It's `verify:lazy-chunks`, inside the
`verify` job — not a per-example step here. Lynx's PrimJS engine is ~ES2019
([level 3](07-verifying.md#level-3--es2019-parse-gate-catches-primjs-issues-locally)),
and `verify:lazy-chunks` acorn-parses (at `ecmaVersion: 2019`) the async chunk a
real `rspeedy build` emits as plain JS. That's the artifact the gate can
actually read: a production `build` packages the dual-thread bundles into a
`.lynx.bundle`/`.web.bundle` **TASM container** (a binary header with JS islands
interleaved between binary sections), which acorn can't parse directly —
confirmed by inspection. The standalone
[`es2019-gate.mjs`](../packages/angular-lynx/verify/es2019-gate.mjs) is a
**local dev-time** helper only: it reads `dist/.rspeedy/main/*.js`, the
un-packaged intermediates that only `rspeedy dev` leaves behind, so it's handy
after a `dev` run but is deliberately **not** in CI (which runs `build`).

### `angular-compat` — the cross-Angular-version leg

angular-lynx ships **partial-Ivy** declarations linked at app-build time, so it
targets its whole `@angular >=21 <23` peer range rather than one version. The `verify`
job runs on the pinned Angular 21, and this job re-pins the workspace to **Angular 22**
and re-runs the suite:

```
node scripts/set-angular-version.mjs <major>   # rewrites the overrides in pnpm-workspace.yaml
pnpm install --no-frozen-lockfile
pnpm --filter angular-lynx build
pnpm --filter angular-lynx typecheck
pnpm --filter angular-lynx verify:all
```

[`scripts/set-angular-version.mjs`](../scripts/set-angular-version.mjs) rewrites
the `overrides:` block in `pnpm-workspace.yaml` to pin the whole Angular toolchain (framework +
`@angular/compiler-cli` + `@ngtools/webpack`, and TypeScript, which 22 needs at 6.0)
to the given major.

The upper bound is on purpose. angular-lynx uses Angular's private bootstrap API
(`ɵinternalCreateApplication` and friends), so a new major can break it at runtime
with a clean build: Angular 22 did, crashing every app with NG0210 until
`provideLynx()` supplied `DOCUMENT`. Add a major here before widening the range.

### `consumer` — what a user gets

[`scripts/verify-consumer.mjs`](../scripts/verify-consumer.mjs), on Angular 21 and
22: packs the tarball, scaffolds every `create-angular-lynx` template outside the
workspace, `npm install`s and builds them, builds a static asset import, and runs
the Vitest quick start from [19 — Testing](19-testing.md). Nothing else covers the
published package's layout: the harnesses alias `angular-lynx` to its source.

## `device-tests.yml` — nightly, on a real engine

Runs the [automated flows](41-device-testing.md#automated-flows) every night and on demand, on Angular
21 and 22, in the pinned Lynx Explorer: the Android emulator on `ubuntu-latest` and the iOS simulator on
`macos-15`. Every job uploads its screenshots, report and engine log, whether it passed or not.

- **Not on pull requests.** A run takes minutes of emulator time and can fail for reasons outside the
  change. GitHub only runs a schedule from the default branch, so nothing runs nightly until this file
  is on `main`.
- **iOS only runs by hand while the repository is private.** macOS minutes count ten times on a private
  repository, and a nightly matrix would use up the free allowance within days. On a public repository
  they're free, and the job joins the schedule by itself.

## `release.yml` — publish to npm with provenance

Triggers when a **GitHub Release is published** (plus a manual
`workflow_dispatch` dry-run that only `npm pack`s). It builds, typechecks and runs
the harnesses, checks the tag against both package versions, then publishes
`angular-lynx` and `create-angular-lynx`:

```
npm publish --provenance --access public
```

- **Provenance** (`--provenance`, `permissions: id-token: write`) publishes a
  signed, verifiable link from the npm package back to this workflow run and
  commit. It needs the `repository` field in `package.json` (present) and npm ≥
  9.5 (Node 22 ships newer). `publishConfig` in `package.json` also sets
  `provenance: true` + `access: public`, so a manual `npm publish` from the
  package dir does the right thing too.
- A **version guard** fails the run if the release tag (`v1.2.3`) doesn't match
  both `package.json` versions — so a mistagged release can't publish.
- The npm automation token is read from the `NPM_TOKEN` repository secret. That
  secret must be configured in the repo settings before the first release;
  everything else is self-contained.

The published tarball (`npm pack --dry-run`) is the `files` allowlist only — the
`dist` folders, the schematics' compiled code and schemas, `bin`,
`forms-theme.css`, `LICENSE`, `README.md` — about 320 kB, no source maps or verify
harnesses. `prepack` builds first, so a manual `npm pack` can't ship a stale `dist`.
