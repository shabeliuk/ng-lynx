# i18n

Angular's i18n mechanism is `$localize` — a global tagged-template function
that either evaluates at runtime (untranslated, "source locale" builds) or
gets replaced with translated text at build time (a real per-locale build).
`ng-lynx` supports the **build-time** path through `pluginAngularLynx`'s
`i18n` option, using the same `@angular/localize/tools` translate mechanism
Angular CLI's own `ng build --localize` uses under the hood — but wired into
this package's own `rspeedy`/`@ngtools/webpack` build (not Angular CLI's
builder, which this project doesn't use at all).

## Only `$localize`-tagged fields, not `i18n="..."` template attributes

Ivy compiles a translatable message two ways, both producing the same
runtime `$localize`-tagged-template call:

- a `$localize` tagged template literal written directly in component
  TypeScript code, e.g. `` $localize`:@@id:Hello!` ``;
- an `i18n="..."` attribute on template text/elements, which ngtsc extracts
  into a `consts` array entry.

**Both forms work.** That wasn't always true, and the history is worth
keeping because the failure mode was so quiet.

The declarative `i18n` attribute doesn't compile to a plain interpolation
call — it compiles to Ivy's `ɵɵi18nStart(elementIndex, constIndex)` /
`ɵɵi18nEnd()` instructions, which build the translated tree through a
separate op-code-driven mutation pass (`i18nStartFirstCreatePass`,
`applyCreateOpCodes`, `i18nApply`, …) rather than the normal per-instruction
element/text creation every other Angular feature in this package goes
through.

**The symptom.** An early version of `examples/i18n` used `i18n="@@title"` on
the first `<text>` and `$localize`-tagged fields for the rest. Live in the
browser preview, the app rendered **only** that first `<text>` element —
empty, with no text content — and nothing after it in the template at all.
**No error was logged anywhere** (console, dev-server output, or the app's
own `LynxErrorHandler`); the render just silently stopped. This package's
`Renderer2` implementation was checked and cleared: `createText`,
`appendChild`, `insertBefore`, `parentNode`, `nextSibling` and `setValue` are
all correct, and every other feature exercising them works fine. This doc
then said the break was "somewhere inside Ivy's i18n op-code machinery
itself, which apparently relies on something about a real DOM node … not
investigated further," and the rule of thumb became *never use the `i18n`
attribute*.

**The actual cause, found later.** It isn't about DOM nodes at all — it's one
missing global. `applyMutableOpCodes` calls
`_locateOrCreateNode(lView, index, opCode, Node.TEXT_NODE)`, reading the
numeric node-type constants straight off the bare DOM global **`Node`**.
Neither target has a DOM: PrimJS has none, and the web preview's Background
Thread is a Web Worker, which has no DOM interfaces either. So the read threw
`ReferenceError: Node is not defined` inside `ɵɵi18nStart`, mid-render —
which is exactly why everything after the first i18n element vanished, and
why nothing user-visible was logged.

`entry-background.ts` now polyfills those constants alongside
`Object.hasOwn` / `TextDecoder` / `AbortController`. It's a class rather than
a plain object because `instanceof Node` appears in Angular's own code
(`instanceof` against a non-callable throws); nothing here ever produces a
real DOM node, so that check is correctly always `false` — and its only
production-reachable use, `isPropertyValid`, already special-cased a missing
`Node` and reaches the identical result either way, so adding the polyfill
changes nothing else.

Reproduced and fixed headlessly: `npm run verify:i18n-attr` asserts the two
things the bug got wrong — the i18n element renders its **text**, and content
**after** it renders — plus that an interpolated i18n block stays reactive to
a later signal write (so `i18nApply` updates work, not just first render).

**Which form should you use?** Either — they're now fully equivalent, both at
runtime and in tooling. `$localize`-tagged fields in the component class
remain the form the rest of this doc (and `examples/i18n`) uses, but the
attribute reads better in a template, and the bundled extractor,
`ng-lynx-extract-i18n`, understands both (see below). This used to be
the one asymmetry left: the extractor originally scanned only `.ts` for
`$localize` calls, so attribute-only messages silently missed the
translation template — a translator would get an incomplete file and those
strings would ship untranslated with no error anywhere.

## Why `$localize` itself is safe on PrimJS

`@angular/localize/init` installs `globalThis.$localize`. Its actual runtime
body (read directly from the installed package's
`fesm2022/_localize-chunk.mjs`, not assumed from documentation) is plain
string concatenation of the tagged-template's literal parts and substituted
expressions — no `TextEncoder`, no `BigInt`, no `fingerprint()` call. Those
show up in `@angular/localize`'s *tools* package (message-id computation, a
build-time-only concern) but never in the runtime tag function itself. So
importing `@angular/localize/init` in the Background-Thread entry point (see
`examples/i18n/src/index.ts`) needs no new PrimJS polyfill.

An untranslated (source-locale) build still needs this import, since its
`$localize` calls run for real at runtime and just interpolate the original
text. A translated (locale-inlined) build doesn't strictly need it — the
build-time inliner (below) replaces every `$localize` call with a plain
string before the code ships — but the example imports it unconditionally so
one entry point works for both cases without a separate translated-only
variant.

## `pluginAngularLynx({ i18n })`

```ts
// lynx.config.uk.ts — a translated-locale build
pluginAngularLynx({
  i18n: {
    locale: 'uk', // informational only — surfaces in diagnostics
    translationFile: './src/locales/uk.json', // resolved from the project root
  },
});
```

The translation file is the `SimpleJsonTranslationParser` format:

```json
{
  "locale": "uk",
  "translations": {
    "title": "Ласкаво просимо",
    "greeting": "Привіт, {$name}!"
  }
}
```

Translation keys are exactly the custom message ids you write in your
`$localize` tags (the part right after `@@`) — see
`examples/i18n/src/app.component.ts` / `src/locales/uk.json` for a complete,
working pair.

### Extracting a translation template — `ng-lynx-extract-i18n`

Rather than hand-copy every id + source string into the JSON, generate the
template with the bundled `ng extract-i18n` equivalent:

It needs esbuild, an optional peer dependency ng-lynx doesn't install for
you: `npm install --save-dev esbuild`.

```bash
ng-lynx-extract-i18n ./src --locale en --out messages.json
# → { "locale": "en", "translations": { "title": "Welcome", … } }
```

It scans `./src` for `.ts` files, extracts every message (id + source text,
placeholders like `{$name}` intact), and writes a
`SimpleJsonTranslationParser`-format template — the same format
`pluginAngularLynx({ i18n })` reads, so a translator fills in the values and
you point `translationFile` at the result. Duplicate ids with conflicting
source text are reported (last wins).

**Both message forms are extracted**, by two different routes, because they
reach the output differently:

- **`$localize` tagged templates** survive a plain TS→JS transform untouched,
  so each file is esbuild-transformed and run through
  `@angular/localize/tools`' `MessageExtractor`.
- **`i18n=` / `i18n-<attr>` attributes** never become `$localize` calls
  without a full template compile, so `MessageExtractor` alone can't see them.
  Instead the `@Component` decorator is read with the TypeScript parser and
  its `template` (or `templateUrl` file) handed to `@angular/compiler`'s own
  `parseTemplate` — whose i18n-marked nodes each carry a `Message` already
  holding the resolved id (your `@@custom` one, or Angular's computed digest)
  and a `messageString` in exactly the `{$PLACEHOLDER}` shape `$localize`
  emits. No serializer or id-hashing of our own, so the two routes can't drift
  apart in format.

Still no `rspeedy build`, no dev server, no ngtsc. (The ids are still yours to
choose; extraction saves the copy-paste, not the naming.) A `template` built
from a template literal *with* `${}` substitutions can't be resolved
statically and is reported as a warning rather than silently skipped.

Verified by `npm run verify:i18n-extract`: the `examples/i18n` assertions
above, plus a fixture covering the attribute route end to end — a
description-prefixed `description@@id`, an interpolation becoming
`{$INTERPOLATION}`, an `i18n-alt` attribute value, a message inside an `@if`
control-flow block, a separate `templateUrl` file, both forms landing in one
output, and un-marked text correctly *not* extracted.

`i18n` **requires AOT** (`aot: true`, the plugin's own default) — it hooks
onto the `angular-aot-ts` rule that only exists on the AOT branch of
`applyAngularCompiler`. Passing `i18n` with `aot: false` throws a clear error
at build-config time rather than silently doing nothing.

### Build once per locale

`pluginAngularLynx({ i18n })` inlines **one locale per build**. To ship
several locales, run `rspeedy build` once per locale, each with its own
config file setting a distinct `output.distPath` and a different `i18n`
value:

```ts
// lynx.config.ts — default / source-locale build (no `i18n` option)
// lynx.config.uk.ts — output.distPath: { root: 'dist-uk' }, i18n: { locale: 'uk', ... }
```

```bash
rspeedy build                         # dist/       (source locale, English)
rspeedy build --config lynx.config.uk.ts   # dist-uk/    (Ukrainian)
```

The dev server takes the same `--config`: in `examples/i18n`, `npm run dev`
serves English and `npm run dev:ua` serves Ukrainian, each with its own QR code.

This mirrors Angular CLI's own classic per-locale output directories
(`dist/en/`, `dist/uk/`, …) — just driven by separate config files instead of
one CLI flag, since there's no single build step here that's expensive
enough to be worth sharing across locales: every `rspeedy build` invocation
already reruns the full AOT TypeScript compile from scratch regardless of
`i18n`, so "build once, inline via post-processing" wouldn't save anything
even if it worked (see below for why it also doesn't work here).

## Why this is a build-time babel pass, not post-build file inlining

Angular CLI's classic i18n workflow inlines translations into an
already-built plain-JS output file, using `@angular/localize/tools`'
`Translator` / `SourceFileTranslationHandler` classes. Two things rule that
approach out for this package, both confirmed empirically rather than
assumed:

1. **Those classes aren't part of `@angular/localize/tools`'s public export
   surface.** Its `package.json` `exports` map has no deep-import wildcard —
   only `Diagnostics`, `MessageExtractor`, the translation parsers/serializers
   (`SimpleJsonTranslationParser`, …), and `makeEs2015TranslatePlugin` /
   `makeEs5TranslatePlugin` / `makeLocalePlugin` are reachable. `Translator`
   and friends exist in the package's source but aren't exported for
   third-party use.
2. **Lynx's packaged `.lynx.bundle`/`.web.bundle` isn't plain JS anyway.**
   Direct inspection shows a binary/wide-char header (a `"SDRAWROF"` magic
   marker plus a JSON config blob in wide-char encoding) before the actual JS
   payload. A real attempt to run Babel's `transformSync` directly against a
   packaged bundle threw `SyntaxError: Unexpected character` immediately — a
   confirmed dead end, not a workaround-needed rough edge. (`grep` without
   `-a` also silently reports zero matches against these files, since it
   auto-detects them as binary — a red herring hit while first checking
   whether `$localize` calls survived packaging.)

So translation has to happen **during** the build, as a webpack/rspack
loader over individual source-derived modules, before Lynx's own packaging
step ever touches the output. `pluginAngularLynx`'s `applyI18nInlining`
(`plugin/src/index.ts`) does this with `makeEs2015TranslatePlugin` — a Babel
plugin factory that rewrites `$localize` tagged-template calls to translated
strings at the AST level — run as a `babel-loader` stage.

**Where that stage hooks in is easy to get wrong, and was gotten wrong on the
first attempt here.** The natural instinct is to mirror the existing Angular
linker rule (`applyAngularLinker`, right above `applyI18nInlining` in
`plugin/src/index.ts`): match `/\.m?js$/`, `enforce: 'pre'`. That produced a
build that succeeded but had **zero effect** — confirmed by a byte-identical
bundle with or without the i18n option set. The reason: the app's own
component code is compiled by ngtools' AOT loader, which is registered on a
rule matching `test: /\.[cm]?ts$/` (`applyAngularCompiler`'s `angular-aot-ts`
rule). Webpack/rspack route a module through its entire loader chain by its
**resolved request path** — the app's `.ts` files stay matched as `.ts` for
their whole chain, even after ngtools compiles them to JS in place. They
never become `.js`-extensioned module requests, so a rule matching
`/\.m?js$/` never touches them at all (it only ever catches genuinely
`.js`/`.mjs` files already on disk — e.g. framework packages in
`node_modules`, which is exactly what the linker rule needs and nothing
more).

The fix: match `/\.[cm]?ts$/` (the same pattern `angular-aot-ts` uses) with
`enforce: 'post'` instead of `'pre'`. `enforce: 'post'` loaders always run
after every `'pre'` and normal loader for a matching module, regardless of
registration order between plugin functions — so the translate pass reliably
sees ngtools' already-compiled-to-JS output without depending on fragile
call-ordering between `applyAngularCompiler` and `applyI18nInlining`.

## Choosing a bundle at runtime is a hosting concern, not this plugin's

`pluginAngularLynx({ i18n })` picks the translated locale **at build time**:
each `rspeedy build` invocation produces one `.lynx.bundle`/`.web.bundle`
baked for exactly one locale. Deciding **which** of those built bundles a
given user actually receives — e.g. based on device/OS locale — happens
*before* any of this package's code runs, the same way a native app picks a
per-locale resource bundle: it's the host app or delivery layer's job (serve
`dist-uk/main.lynx.bundle` to devices reporting a `uk` locale, `dist/` to
everyone else), not something `ng-lynx` can influence from inside the
bundle that's already been selected and loaded.

[`lynxGlobalProps()`](17-host-data.md) is a different mechanism: it exposes
data pushed into an **already-running** card (theme, host context, and yes,
optionally a locale-like hint), reactively, as a signal — useful for
in-app behavior that should react to a *runtime* value without a full
separate build per variation (e.g. toggling a date format). It is not a way
to select which locale-inlined bundle gets loaded in the first place — by the
time a card is running and `lynxGlobalProps()` is readable, the `$localize`
calls in that bundle have already been build-time-inlined (or left as
live, English, source-locale calls) for good. Don't reach for `globalProps`
to solve locale switching; reach for it only if your app wants some
additional runtime-reactive behavior *on top of* the build-time locale
that bundle already shipped with.

## Verifying

Unlike the `harness-*.ts` suite (esbuild + mock PAPI), inlining translations
is a real build-pipeline concern — there's no PAPI-level behavior to mock.
`npm run verify:i18n` (`verify/i18n-build.mjs`) runs two real `rspeedy
build`s of `examples/i18n` (the default source-locale config and
`lynx.config.uk.ts`) and asserts directly on the packaged
`main.web.bundle` content: the source-locale build still has the original
English strings; the uk build has the real Ukrainian translations
(including the interpolated `greeting` message, with its static template
parts intact around the substituted name) and does **not** still contain
any of the untranslated English source strings — proving the babel pass
actually replaced them rather than merely adding translated text somewhere
else in the bundle. (The script reads bundles as `'utf8'`, not `'latin1'`
like `lazy-chunks.mjs`'s binary-asset checks — a `'latin1'` read never
matches genuine multi-byte Cyrillic string literals, since it reinterprets
each UTF-8 byte as its own character; found by the same script failing all
of its uk-locale assertions on the first run.)

Beyond that script, this was also confirmed:

- **Live, in the dev-server preview**: both `examples/i18n` (default,
  English, no `i18n` option) and a second config
  (`lynx.config.uk.ts` → `dist-uk/`, Ukrainian) render their full template
  correctly in the web preview — title, computed greeting, subtitle, button,
  and (after tapping the button) the response text — confirmed by reading
  the actual rendered `x-text`/`raw-text` DOM nodes in both locales.
- **The `i18n="..."` attribute pitfall above** — confirmed by deliberately
  reproducing it, then fixing it, in the same live preview.
- **Extraction** (`ng-lynx-extract-i18n`) — `npm run verify:i18n-extract`
  extracts every message from `examples/i18n/src`, checks the ids/text/
  placeholders, that the output round-trips through the plugin's own
  `SimpleJsonTranslationParser`, and that its ids match `uk.json`'s keys.

If you add this option to your own app, the fastest sanity check is the same
one used here: build (or run dev) once per config, then read back the
rendered text nodes (or `grep -a` the packaged bundle for your translated
strings — remember the `-a` flag, see above) rather than trusting a
successful build alone.
